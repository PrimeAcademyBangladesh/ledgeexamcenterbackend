# Lead Edge Ltd — Complete API Contract Reference (DRF)

> **Single source of truth** for all frontend ↔ backend API endpoints.
> All endpoints expect `Content-Type: application/json`.
> Authenticated endpoints require `Authorization: Bearer <access_token>`.
> Base URL: configured via `VITE_API_BASE_URL` environment variable.
> **Last verified:** 2026-04-12 — cross-checked against all frontend service files and TypeScript types.

---

## Backend Build Guidance

- The production backend is a separate **Django REST Framework (DRF)** API.
- The frontend is a React SPA and must consume the DRF API through the service layer in `src/services/api/`.
- Do not integrate payment providers: payment is handled manually by the office.
- Use JWT authentication with access + refresh tokens.
- Use `djangorestframework-simplejwt` for JWTs and `djangorestframework-camel-case` so API payloads match the frontend camelCase TypeScript types.
- All server-side authorization must be enforced by DRF permissions, not only frontend role checks.
- Learner-facing exam data must never include `correctAnswers` or explanations before submission.
- When `VITE_API_BASE_URL` is not configured, the frontend can continue using mock services; when it is configured, requests should hit the real DRF API.

### Frontend API Service Layer

The frontend API integration is organized under `src/services/api/`:

| File | Purpose |
|------|---------|
| `client.ts` | Shared API client, base URL config, auth headers, error handling |
| `auth.ts` | Login, logout, refresh, current user |
| `questions.ts` | Question bank CRUD |
| `exams.ts` | Exam configs, sessions, PIN validation, submission |
| `learners.ts` | Learner registration, profile, results |
| `invigilators.ts` | Invigilator management and assignments |
| `retakes.ts` | Resit eligibility and resit session creation |
| `types.ts` | Shared request/response TypeScript interfaces |

### Critical Business Rules for DRF

- Exam PINs are **6 numeric digits**.
- PINs are system-generated by default, but admins/invigilators may override them for operational issues.
- Learners must never be allowed to edit a session PIN.
- A resit is only available when the learner failed within **10 percentage points** of the pass boundary.
- Only invigilators/admins can create a resit.
- Resit sessions must use a fresh persisted question set excluding questions the learner has already seen.
- If the learner fails outside the 10% margin, a new exam booking is required instead of a resit.
- Active exam progress must autosave to the DRF database every 5–10 seconds and after each answer.
- Learners who lose connection or close the browser must be able to re-enter the same session PIN and resume from the latest saved draft.
- PIN validation, resume, autosave, and submit must always use the existing frozen `ExamSession.question_set`; only session creation may randomise questions.

## Step-by-Step DRF Implementation Sequence

Build the backend in this order. Do not start the exam runtime endpoints before the models, serializers, permissions, and question-selection service are complete.

### Step 1 — Project setup and shared API conventions

1. Install required packages:
   - `djangorestframework`
   - `djangorestframework-simplejwt`
   - `djangorestframework-camel-case`
   - `django-cors-headers`
2. Configure JWT auth, camelCase JSON parsing/rendering, CORS, pagination, and token blacklist support.
3. Set frontend `VITE_API_BASE_URL` to the DRF API base URL when the real backend is ready.
4. Keep all API responses in camelCase because the frontend TypeScript types already expect camelCase.

### Step 2 — Authentication and roles

1. Create the custom `User` model with roles: `admin`, `invigilator`, `learner`.
2. Use email as the login username.
3. Implement JWT login, refresh, logout, and current-user endpoints first:
   - `POST /api/auth/login/`
   - `POST /api/auth/refresh/`
   - `POST /api/auth/logout/`
   - `GET /api/auth/me/`
4. Add DRF permission classes before building protected endpoints:
   - `IsAdmin`
   - `IsInvigilator`
   - `IsLearner`
   - session-owner checks for learner exam endpoints
5. Never rely only on frontend role checks. Every protected action must be checked server-side.

### Step 3 — Core admin data models

Create and migrate these models first:

1. `Qualification`
2. `Question`
3. `ExamConfig`
4. `ReasonableAdjustment`

Then implement these admin endpoints:

1. `GET /api/qualifications/`
2. `POST /api/qualifications/`
3. `GET /api/questions/`
4. `POST /api/questions/`
5. `PUT /api/questions/{id}/`
6. `DELETE /api/questions/{id}/`
7. `POST /api/questions/bulk-import/`
8. `GET /api/exams/`
9. `POST /api/exams/`
10. `GET /api/exams/{id}/`
11. `PUT /api/exams/{id}/`

Important rules:

- `Question.correct_answers` and `Question.explanation` are admin-only fields.
- Learner exam responses must never include correct answers or explanations.
- `ExamConfig.questions_per_exam` controls how many questions are selected for each generated paper.

### Step 4 — Learners and invigilators

Implement user-management endpoints after auth and core admin models:

1. `GET /api/learners/`
2. `POST /api/learners/`
3. `GET /api/learners/{id}/`
4. `PUT /api/learners/{id}/`
5. `PATCH /api/learners/{id}/status/`
6. `GET /api/invigilators/`
7. `POST /api/invigilators/`
8. `GET /api/invigilators/{id}/`
9. `PUT /api/invigilators/{id}/`
10. `PATCH /api/invigilators/{id}/status/`

Important rules:

- `POST /api/learners/` creates a `User` with `role=learner`.
- `POST /api/invigilators/` creates a `User` with `role=invigilator`.
- Admin-only writes must be enforced by permissions.

### Step 5 — Exam session and seen-question models

Create and migrate these models before building any start/resume/submit endpoint:

1. `ExamSession`
2. `LearnerSeenQuestion`
3. `IntegrityViolation`
4. `ExamResult`
5. `RetakeRequest`

Important database requirements:

- `ExamSession.question_set` must store the frozen selected questions for that session.
- `LearnerSeenQuestion` must track every question delivered to each learner.
- Add a unique constraint on `LearnerSeenQuestion(learner, question)`.
- Save draft fields directly on `ExamSession` so learner progress survives browser close, computer restart, or network failure.
- Add a database-level guard or serializer validation so a session cannot move to `scheduled`/`in_progress` without the required frozen `question_set` count.

### Step 6 — Build the reusable question-selection service

Create one backend service function and reuse it for normal sessions and resits.

Required service behaviour:

1. Receive `exam_config`, `learner`, and optional `previous_result`.
2. Get the qualification from `exam_config.qualification`.
3. Read `required_count = exam_config.questions_per_exam`.
4. Query `LearnerSeenQuestion` for that learner and qualification.
5. Filter active questions by qualification.
6. Exclude all previously seen question IDs.
7. Randomly select exactly `required_count` questions.
8. If not enough unseen questions exist, raise `400 Bad Request`.
9. Return the selected `Question` objects.

Use this rule for both first exams and resits if the client requirement is “never repeat questions for the same learner”.

Hard enforcement checklist:

- Treat `LearnerSeenQuestion` as the single source of truth for questions already delivered to a learner.
- Mark questions as seen immediately when `ExamSession.question_set` is created, not after submit.
- Run selection, `question_set` save, and seen-question creation inside one `transaction.atomic()` block.
- Keep `UniqueConstraint(learner, question)` so duplicate delivery is blocked at database level.
- Never use only `ExamResult.question_ids` to decide seen questions because abandoned/in-progress sessions must also count as seen.
- Do not generate a replacement question set for a cancelled, restarted, resumed, or PIN-validated session. Create a new session only if policy allows, and that new session must exclude all existing `LearnerSeenQuestion` rows.

### Step 7 — Create scheduled exam sessions

Implement `POST /api/exams/sessions/` only after Step 6 is complete.

Backend sequence for session creation:

1. Validate admin permission.
2. Validate `examConfigId`, `learnerId`, `invigilatorId`, date, and time.
3. Generate a 6-digit numeric PIN if one is not provided.
4. Calculate `pin_window_start = scheduled time - 5 minutes`.
5. Calculate `pin_window_end = scheduled time + exam time + extra time`.
6. Start a database transaction.
7. Create `ExamSession`.
8. Call the question-selection service.
9. Save selected questions into `ExamSession.question_set`.
10. Immediately create `LearnerSeenQuestion` records for the selected questions using `bulk_create(..., ignore_conflicts=True)`.
11. Return the `ExamSession` response with `questionIds`.

Do not allow the frontend to send or choose question IDs.

Before returning success, assert that:

- `ExamSession.question_set.count() == exam_config.questions_per_exam`.
- Every selected question belongs to `exam_config.qualification`.
- No selected question already existed in `LearnerSeenQuestion` for this learner before selection.
- The matching `LearnerSeenQuestion` rows now exist for every selected question.

### Step 8 — PIN validation and resume flow

Implement `POST /api/exams/validate-pin/` after sessions can be created with frozen question sets.

Backend sequence:

1. Validate learner authentication.
2. Load the session by `sessionId`.
3. Confirm the learner owns the session.
4. Confirm `pin` matches and `pin_active=true`.
5. Confirm current time is inside the PIN window.
6. If this is the first entry, set `status='in_progress'` and set `started_at`.
7. Assert `ExamSession.question_set` already exists and contains the configured number of questions.
8. Load questions from `ExamSession.question_set` only. Never call the question-selection service and never randomise here.
9. Preserve the stored `question_set` order when serialising learner-safe questions without `correctAnswers` or `explanation`.
10. Return saved draft fields if they exist:
   - `answers`
   - `currentQuestionIndex`
   - `flaggedQuestionIndexes`
   - `remainingSeconds`
   - `updatedAt`
11. Calculate authoritative remaining time from `started_at`, exam duration, and extra time.

This is the resume flow: learner logs back in, enters the same session PIN, and receives the same frozen questions plus the latest saved draft position.

### Step 9 — Autosave draft progress

Implement `PATCH /api/exams/sessions/{sessionId}/draft/` immediately after PIN validation.

Backend sequence:

1. Validate learner authentication and session ownership.
2. Accept autosave only when `session.status='in_progress'`.
3. Reject autosave if the authoritative server timer has expired.
4. Validate every submitted `questionId` belongs to `ExamSession.question_set`.
5. Save to `ExamSession.draft_answers`.
6. Save `draft_current_question_index`.
7. Save `draft_flagged_question_indexes`.
8. Save `draft_remaining_seconds` as UI restore data only.
9. Set `draft_updated_at=timezone.now()`.
10. Return the saved draft response.

Frontend calls this endpoint every 5–10 seconds and immediately after each answer change.

### Step 10 — Submit and score exam

Implement `POST /api/exams/{sessionId}/submit/` after autosave is complete.

Backend sequence:

1. Validate learner authentication and session ownership.
2. Validate session is `in_progress`.
3. Validate all submitted question IDs belong to the frozen `question_set`.
4. Score answers server-side using `Question.correct_answers`.
5. Calculate score percentage, grade, pass/fail, and attempt number.
6. Create `ExamResult`.
7. Link any `IntegrityViolation` records to the result.
8. Mark session as `completed`.
9. Return the result response.

Never send correct answers to the learner in the submit response.

### Step 11 — Resit and retake flow

Implement retake endpoints after results and session creation are stable.

Retake request sequence:

1. Learner calls `POST /api/retakes/request/`.
2. Backend validates previous result belongs to learner.
3. Backend prevents duplicate pending requests for the same exam/result.
4. Admin reviews with approve or deny endpoint.

Resit session sequence:

1. Admin/invigilator calls `POST /api/retakes/resit/` or creates a session with `previousResultId`.
2. Backend loads the previous `ExamResult`.
3. Backend confirms the learner failed but was within 10 percentage points of the pass mark.
4. Backend calls the same question-selection service.
5. The service excludes all questions already in `LearnerSeenQuestion`.
6. If not enough unseen questions exist, return `400 Bad Request` with: `Not enough unseen questions available. Add more questions to this qualification before creating a resit.`
7. Create the new frozen `ExamSession.question_set`.
8. Mark the selected questions as seen immediately.

### Step 12 — Integrity violations

Implement `POST /api/violations/` after active exam sessions work.

Backend sequence:

1. Validate learner authentication and session ownership.
2. Accept violation only while session is active.
3. Create `IntegrityViolation`.
4. Return `strikeCount` for the current session.
5. On exam submit, link violations to the final `ExamResult`.

### Step 13 — Results, reports, and adjustments

Implement these after core exam flow is complete:

1. `GET /api/results/`
2. `GET /api/results/{id}/`
3. `GET /api/results/{id}/marksheet/`
4. `GET /api/reports/`
5. `GET /api/reports/export/`
6. `GET /api/adjustments/`
7. `POST /api/adjustments/`
8. `PUT /api/adjustments/{id}/`

Learners must only see their own results. Admins can see all results and reports.

### Step 14 — Final integration test order

Test the complete flow in this order:

1. Admin login works.
2. Admin creates qualification.
3. Admin imports enough questions for the qualification.
4. Admin creates published exam config.
5. Admin creates learner and invigilator.
6. Admin schedules exam session.
7. Backend freezes random question set and records seen questions.
8. Learner logs in and validates PIN.
9. Learner answers questions.
10. Draft autosaves after each answer and every 5–10 seconds.
11. Learner closes browser or loses network.
12. Learner logs back in, enters same PIN, and resumes from latest draft.
13. Learner submits exam.
14. Backend scores and stores result.
15. If failed within 10%, create resit.
16. Resit uses fresh unseen questions only.
17. If not enough fresh questions exist, backend blocks resit and tells admin to add more questions.

## API Endpoints

> All list endpoints use `PageNumberPagination` (`page_size=50`) and return:
> ```json
> { "count": N, "next": "url|null", "previous": "url|null", "results": [...] }
> ```
> Exceptions noted per endpoint.

### 1. Authentication

#### POST /api/auth/login/
**Auth:** None
**Payload:**
```json
{ "email": "string", "password": "string" }
```
**Response (200):**
```json
{
  "access": "jwt-access-token",
  "refresh": "jwt-refresh-token",
  "user": {
    "id": "uuid",
    "email": "string",
    "firstName": "string",
    "lastName": "string",
    "role": "admin | invigilator | learner",
    "uln": "string | null",
    "providerCode": "string | null"
  }
}
```
**DRF:** Use `djangorestframework-simplejwt` + `djangorestframework-camel-case` for automatic camelCase serialization.

#### POST /api/auth/refresh/
**Auth:** None
**Payload:**
```json
{ "refresh": "jwt-refresh-token" }
```
**Response (200):**
```json
{ "access": "new-jwt-access-token" }
```

#### POST /api/auth/logout/
**Auth:** Bearer token
**Payload:** `{ "refresh": "jwt-refresh-token" }`
**Response:** `204 No Content`
**DRF:** Blacklist the refresh token via `rest_framework_simplejwt.token_blacklist`.

#### GET /api/auth/me/
**Auth:** Bearer token
**Response (200):** Same `user` object shape as login response.

### Question Bank + Frozen Session Implementation Guideline

Use this backend flow instead of manually maintaining fixed paper sets only:

1. **Maintain a question bank per qualification**
   - Admins add many active questions under each `Qualification`.
   - `ExamConfig.questions_per_exam` controls how many questions are selected for a paper.
   - Optional metadata such as `tags` and difficulty can be used later for balanced selection.

2. **Create `ExamSession`**
   - Validate learner, invigilator, exam config, schedule, PIN window, and resit eligibility if `previousResultId` is provided.
   - Never let the frontend choose question IDs.

3. **Select random unseen questions**
   - Get all questions already delivered to the learner from `LearnerSeenQuestion` for the same qualification.
   - Filter active questions by qualification and exclude those seen IDs.
   - Randomly select exactly `questions_per_exam` questions.
   - If fewer unseen questions are available than required, return `400 Bad Request` with a clear admin-facing message, for example: `Not enough unseen questions available. Add more questions to this qualification before creating a resit.`

4. **Save selected question IDs into `ExamSession.question_set`**
   - Persist the selected questions once at session creation.
   - All later PIN validation, autosave, resume, and submit endpoints must read from this frozen `question_set`.
   - Never re-randomise after the session is created, otherwise resume and audit integrity break.

5. **Mark selected questions as seen for that learner**
   - Create `LearnerSeenQuestion` records immediately after saving `question_set`, not after submission.
   - This protects against learners seeing questions, disconnecting, and receiving the same questions again.
   - Use `bulk_create(..., ignore_conflicts=True)` with the unique learner/question constraint.

6. **Resit-specific flow**
   - Load the previous failed `ExamResult`.
   - Confirm the learner failed within the allowed 10 percentage point margin.
   - Get the learner's previously seen question IDs.
   - Exclude those IDs from the question bank.
   - Select fresh questions only.
   - If not enough unseen questions exist, block the resit and tell the admin to add more questions.

**DRF pseudo-code:**
```python
from django.db import transaction
from django.utils import timezone

@transaction.atomic
def create_exam_session(*, exam_config, learner, invigilator, previous_result=None, **data):
    qualification = exam_config.qualification
    required_count = exam_config.questions_per_exam

    if previous_result:
        pass_mark = exam_config.grade_pass
        if previous_result.passed or previous_result.score_percent < pass_mark - 10:
            raise ValidationError("Learner is not eligible for a resit.")

    seen_ids = LearnerSeenQuestion.objects.filter(
        learner=learner,
        qualification=qualification,
    ).values_list("question_id", flat=True)

    available_questions = Question.objects.filter(
        qualification=qualification,
        is_active=True,
    ).exclude(id__in=seen_ids)

    if available_questions.count() < required_count:
        raise ValidationError(
            "Not enough unseen questions available. Add more questions to this qualification before creating a resit."
        )

    selected_questions = list(available_questions.order_by("?")[:required_count])

    session = ExamSession.objects.create(
        exam_config=exam_config,
        learner=learner,
        invigilator=invigilator,
        **data,
    )
    session.question_set.set(selected_questions)

    LearnerSeenQuestion.objects.bulk_create(
        [
            LearnerSeenQuestion(
                learner=learner,
                qualification=qualification,
                question=question,
                session=session,
            )
            for question in selected_questions
        ],
        ignore_conflicts=True,
    )

    if session.question_set.count() != required_count:
        raise ValidationError("Frozen question set was not created correctly.")

    return session
```

**Client recommendation wording:**
> We should not manually create fixed paper sets only. The better secure approach is to maintain a large question bank per qualification. When an exam starts, the backend generates and freezes a random question set for that learner. For retakes, the system excludes all questions the learner has already seen, so they receive a fresh paper. Multiple question sets can work, but the strongest solution is: question bank + random generated frozen session + seen-question tracking for resits.

```python
def score_exam(answers, exam_config):
    questions = Question.objects.filter(id__in=[a['question_id'] for a in answers])
    correct = 0
    for answer in answers:
        q = questions.get(id=answer['question_id'])
        if sorted(answer['selected']) == sorted(q.correct_answers):
            correct += 1
    total = len(answers)
    pct = round((correct / total) * 100)
    boundaries = {
        'distinction': exam_config.grade_distinction,
        'merit': exam_config.grade_merit,
        'pass': exam_config.grade_pass,
    }
    if pct >= boundaries['distinction']:
        grade = 'distinction'
    elif pct >= boundaries['merit']:
        grade = 'merit'
    elif pct >= boundaries['pass']:
        grade = 'pass'
    else:
        grade = 'did_not_pass'
    return pct, correct, grade, pct >= boundaries['pass']
```

**Frozen question-set enforcement before scoring:**
```python
def get_frozen_session_questions(session):
    question_ids = list(
        session.question_set.order_by("examsessionquestion__position")
        .values_list("id", flat=True)
    )
    expected_count = session.exam_config.questions_per_exam
    if len(question_ids) != expected_count:
        raise ValidationError(
            "Exam session has no valid frozen question set. Ask an admin to recreate the session."
        )
    return question_ids

def validate_answers_against_frozen_set(session, answers):
    frozen_ids = set(get_frozen_session_questions(session))
    answer_ids = {answer["question_id"] for answer in answers}
    if not answer_ids.issubset(frozen_ids):
        raise ValidationError("Submitted answers include questions outside this exam session.")
```
